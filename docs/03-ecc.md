# 03 · ECC 与 OOB

## 1. 为什么是"软件算 ECC"

这颗 SoC 的 NFI 自带硬件 ECC 引擎：只要配置正确，控制器会自己算校验并写进备用区，
软件只需把 OOB 缓冲填 `0xFF`。
我们试过两条硬件路线，**都失败**：

| 路线 | 做法 | 结果 |
|---|---|---|
| 控制器寄存器 | 补 `0x60–0x6C` / `0x21C` / 全套 boot0 值（含 `0xB0–0xBC`）三种配置 | 前两种无效果，第三种**控制器挂死**；写入成功但 **OOB 仍全 `FF`** |
| 芯片片上 ECC | `SET FEATURE(0xB0) = 0x19` | 写 8 页后读回：**OOB 仍全 `FF`**，芯片什么都没生成 |

于是只能**从数据侧反推**：采集设备上真实存在的 OOB，当成一个 GF(2) 上的线性映射解出来。
好处是**可验证**——每一页都能逐字节比对；硬件那条路只能靠"能不能开机"判断。

## 2. OOB 的 78 字节结构

```
段 0（管主区 0…1023）              段 1（管主区 1024…2047）
偏移  0   1   2   3 | 4 … 31 | 32…38    39  40  41  42 | 43 … 70 | 71…77
     FF  D4  40  FF | ECC0(28B)| FF×7   FF  D4  40  FF | ECC1(28B)| FF×7
                   └ 224 bit ┘                            └ 224 bit ┘
```

- 每段 **39 字节**：4 字节头 + **28 字节校验** + 7 字节 `FF`
- 校验位落在 **`4…31`** 和 **`43…70`**（早期文档写成 1 起是错的，已纠正）
- 备用区实际是 **78 字节**，不是常见的 64 字节——这是这颗 UNIM 芯片的特点

## 3. ECC 映射

### 3.1 形式

对一段 1024 字节（8192 bit）数据：

```
ECC(224 bit) = M · data(8192 bit) ⊕ c
```

- `M` 是 8192 × 224 的 0/1 矩阵，`c` 是常数项
- 实测常数项为 0（全零数据 ⇒ 全零校验）
- 两段用**同一套**映射（已验证 `sol0 == sol1`）

### 3.2 怎么得到的（可复现的方法）

1. 用 `0xFE` 类命令从设备上批量采集"数据页 → OOB"样本；
2. 把每个样本展开成 `8192` 个 0/1 变量、`224` 个方程；
3. 在 GF(2) 上解线性方程组（高斯消元），得到 8193 行结果（8192 数据位 + 1 常数位）；
4. 校验：矩阵**满秩 8193、零矛盾**；用它预测未参与求解的页，逐字节一致。

> 结论：这是一个**纯线性**映射，没有非线性项、没有位置相关的特殊规则。

### 3.3 压缩：224 阶线性递推

直接存整张表是 `8193 × 28 B ≈ 229 KB`，对 27 KB 的镜像不可接受。

用 **Berlekamp–Massey** 求它的最小线性递推：

```
行 i  =  Σ  c_k · 行(i-1-k)      （k = 1…224，c_k ∈ {0,1}）
```

- 递推阶数 **224**，非零系数 **106 个**
- 重算校验：**8192 / 8193 行完全一致**（第 8193 行是常数行，本来就全 0）

所以镜像里只存：

| 内容 | 大小 |
|---|---|
| 224 行种子（`ecc_seed[224][7]`） | 6 272 B |
| 224 bit 系数（`ecc_recur[7]`） | 28 B |
| `.rodata` 合计（含对齐/其它） | 6 940 B |

启动时展开成 `ecc_tab[8193][7]`（229 KB，在 BSS 里），**一次性 ~几十毫秒**。

## 4. 代码

### 4.1 `ecc_build()`

```c
// 1) 拷 224 行种子
// 2) 对 i = 224 … 8192：
//       acc = 0
//       for k in 0…223: if c_k: acc ^= tab[i-1-k]
//       tab[i] = acc
```

### 4.2 `ecc_fill_oob(pg, oob)`

```c
for (i = 0; i < 1024; i++) {          // 字节作外层，位作内层
    b0 = pg[i]; b1 = pg[1024 + i];
    if ((b0 | b1) == 0) continue;
    for (k = 0; k < 8; k++) {
        if (b0 >> k & 1) a0 ^= ecc_tab[i*8 + k];
        if (b1 >> k & 1) a1 ^= ecc_tab[i*8 + k];
    }
}
// 按 §2 的结构把 a0 / a1 写进 oob[4..31] / oob[43..70]
```

> **为什么"字节作外层"**：早期写法是 `for i in 0…8191`、每次 `pg[i>>3]`，
> 同一个字节被读 8 遍。改成字节外层后内存读少 8 倍（在 cache 关着时是 13 ms → 5 ms/页；
> 开了 cache 之后影响不大，但保留这个写法没有坏处）。
>
> **位序**：`i*8 + k` 与原位序 `i` 完全等价——改动时用全量对拍验证过（313 页抽样、0 不符）。

## 5. 验证记录

| 项 | 结果 |
|---|---|
| 映射满秩 | 8193 / 8193，零矛盾 |
| 目标镜像全量 | **4376 / 4376 页** 与设备实测 OOB 逐字节一致 |
| 跨设备 | 用 A 机解出的映射预测 B 机 256 页，**全对** |
| 固件实算 vs 参考实现 | 写 8 页后读回 OOB，**8/8 页逐字节一致** |
| 整分区实刷 | 三分区刷完设备正常开机（ECC 错则过不了启动校验） |

## 7. 踩坑清单

| 坑 | 症状 | 正确做法 |
|---|---|---|
| 以为 OOB 是 64 B | 写进去的 OOB 只覆盖前 64 字节，设备起不来 | 这平台是 **78 B**（2×39） |
| 把表展开放在写页路径里 | 第一个 16 KB 帧就超时（主机只等 1000 ms） | **启动时展开**（main 第 5 步） |
| 硬件 ECC 只差"一个开关" | 反复配寄存器，OOB 一直全 `FF` | 两条硬件路都走不通，别回头 |
| 用 8 页小测试判断 ECC 对错 | 会误报（页 0/1 的写入顺序干扰） | 必须**整块 64 页**、按 `[2..63, 1, 0]` 顺序 |
